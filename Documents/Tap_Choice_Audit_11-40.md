# Tap-choice audit: Levels 11–40

Generated by `auditTapChoices` in the production `ChainSimulation`; run with:

```powershell
flutter test test/tap_choice_audit_test.dart --reporter expanded
```

Every candidate starts in a fresh world and is tapped at its configured object center. **Success** means the target is reached. **Failed** means the chain runs but misses the target. **Full** counts successful routes that also touch every dynamic object. The `starter` remains the authored timeout/default start; other target-reaching candidates are measured alternate starts, not rejected by the validator.

The optional level allowlist uses object IDs. If absent, it preserves compatibility by making all dynamic objects tappable. Level 21 opts in explicitly with seven candidates. Static scenery and sensors are not direct tap candidates. In the audited levels, no dynamic object is currently physics-only by tap policy; every dynamic object is a plausible player choice, including the unsuccessful decoys listed below. Designers can opt a dynamic object out without affecting contact physics.

## Engine behavior and safeguards

- `TapChainGame.handleTap` converts screen coordinates and asks the simulation to start only while waiting. `ChainSimulation.triggerAt(point)` now filters direct taps through `LevelConfig.tapCandidates`; a null allowlist retains legacy all-dynamic behavior. Timeout/default `trigger()` still uses the single authored `starter`.
- A direct non-starter candidate retains its existing generic impulse toward its nearest dynamic neighbor; the authored `starter` uses its authored push, and directly tapped pets run. A candidate restriction does not change any impulse or collider.
- Forge2D collisions still contact all bodies. Physics-triggered switch, spring, and pet behavior is separate from player eligibility. `PhysicsObject.playerTapped` and `physicsActivated` record the two sources independently. The simulation's global `triggered` guard allows only the initial tap; switch/spring/pet one-shot flags prevent repeat activation.
- The generator's existing physics validation still checks the authored starter. `auditTapChoices` creates and settles a fresh production physics world for each configured candidate and reports its actual target/full-touch result; it does not run during gameplay or override physics outcomes.
- Levels 1–10 have no allowlist/profile assigned, so their existing all-dynamic tap behavior is unchanged. Levels 11–40 retain their current structures. Levels 11–40 have broad/narrow/exact count profiles validated against actual target-reaching outcomes.

The audit identifies alternate successful taps, but current level data only marks one default `starter`; it does not separately declare which alternate successes are design-intended. The profile controls the intended count band, while the audit reports the exact measured IDs. Level 21 is explicit and exact (1 of 7); Level 35 is another exact level (1 of 7). Levels 22, 26, and 30 preserve their two-shelf, pet-race, and gated-pet structures and have respectively 4/12, 3/7, and 3/7 successful target taps.
